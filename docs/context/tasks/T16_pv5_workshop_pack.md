# T16 — PV5 action-distinctness: workshop pack

**Track A** · **Depends:** T08, T14 · **PROD round trip:** No — assembles results already returned

**Goal.** Assemble the materials for the business session that tests whether each
persona class implies a *different action*. The workshop itself is a business meeting,
not a coding task — this task produces the pack that makes it decisive.

**Why.** PV1–PV4 establish that the axes are buildable, novel, outcome-relevant and
additive. None of that proves they are **useful**, which is a question only collections
can answer: if two classes lead to the same action, the distinction is decorative and
the classes should be merged (S7 keeps the grid small). This is the last gate before
anything is operationalised, and the one the whole persona premise is ultimately for.

**Load.** `RESULTS.md` (gate outcomes and returned outputs);
`reference/domain_and_decisions.md §3` for the decision graph the axes must serve.
No new data — everything needed has already come back from earlier tasks.

## Steps

1. **One page per axis class.** For each surviving A4 and A2 class: what it means in
   plain language, its share of the book, its realised cure/recovery rates (from T08 /
   T14), and two or three anonymised illustrative profiles built from aggregate
   characteristics — **not** real customer records (R18 governance).
2. **The grid.** Persona class × score band, with cell volumes. Flag any cell too thin
   to staff a distinct treatment.
3. **State what is NOT claimed.** The axes describe *mechanism*; they do not establish
   that any treatment causes better recovery (X6). Any historical action/outcome
   crosstab included must be headed as correlational and confounded by indication —
   officers did not assign actions randomly.
4. **The question to put to the room, per class:** *"What would you do differently for
   this group than for the others?"* Record the answers verbatim.
5. **Merge rule, agreed in advance:** two classes drawing the same answer get merged.
   Say this before the discussion so the outcome is not negotiated afterwards.

## Decision rule

- **Each class draws a distinct action** → PV5 passes; the axis ships as a
  segmentation and the business owns the action mapping from here (division of labour,
  `domain_and_decisions.md §1`).
- **Some classes collapse** → merge them, update the class definitions, and re-run T08
  on the merged scheme (cheap — no rebuild, just re-aggregation).
- **No class draws a distinct action** → the axis has no operational value even if it
  passed every statistical gate. Record that plainly; it is a real result, and a
  cheaper one to discover here than after deployment.

## Done when

The pack is committed to the repo, the session has happened, and the answers plus the
resulting merge/keep decisions are logged in `RESULTS.md` under the persona gate table.
Any class merge is reflected in the class definitions and flagged for a T08 re-run.
