## Clear bugs

### S6-Q01 [A4 · `_dpd_journey/history.py:60-64,155-163`, `_dpd_journey/spark.py:300-307`] A later unresolvable gap removes the state of earlier spine rows
Now: Stage 1 builds one history per account over all months up to `persona_end_date`. An
unresolvable gap (with the default `on_unresolvable_gap: truncate`) sets `cut` to the month after
the gap, so `first_month` moves past every month before it. Stage 2 then drops every spine row
whose month is before `first_month` (`_trunc_len < 1`). A spine row in a month **before** the gap,
whose history up to its own date is complete, gets no A4 row at all. Reproduced locally on
`build_history`: months 0–5 at `0 0 2 3 4 5`, months 6–9 missing, months 10–12 at `8 9 9` →
`first_month_idx = 10`, `buckets = [8, 9, 9]`; a spine row at month 5 is dropped, although its
own history (clean start, straight roll) would classify. With `drop` the whole account loses every
row. Rows after the gap are correct (cropped). Related, smaller: a spine row inside a filled gap
reads months filled from the gap's right neighbour, which lies after its date.
Spec/expected: the Stage 2 docstring says a row is dropped only when there is "no billing
history at this date"; METHODOLOGY §2 calls the repair causal ("a state assigned today does not
change when next month's digit arrives"); D5/D6 require point-in-time. Here a future gap changes
(removes) a past state.
Options: (a) keep; document that a later gap removes earlier rows. (b) In the A4 bundle, resolve the
history per spine row: run the gap fill on the slice up to the row's month (or keep the full grid
and the cut points, and apply only cuts at or before the row's month).
Recommendation: (b). Only past persona months are affected (the latest month is never before a gap
it has seen), so the latest-month PROD output barely moves; the trend / vintage sheets and A3's
anchor (D-A3-2) read past months.
Impact: rows of accounts with `n_months_truncated > 0` (or `build_status =
'dropped_unresolvable_gap'`) whose spine month is before `first_month`; the A4 check can count them
as spine rows without an A4 row, per model_id. Expect few at CC (gap fill is generous, the 2024-01
floor removes the 2021–23 gap) and few at RL.

### S6-Q02 [shared · `_common.py:182-190` (`_obs_base`), RL path] RL obs base keeps an arbitrary `cif_id` for a duplicated grain row
Now: `build_rl_obs_base` selects `(account_id, observation_date, cif_id)` and then
`dropDuplicates(GRAIN)`. If `rl_spine` holds the same account-month twice with different `cif_id`
(or one NULL), the row kept is arbitrary: reruns can disagree, and a NULL can win over a real CIF,
which removes every customer signal of the row (A1 Unknown / no distress, A2 location `no_evidence`).
CC collapses the same case to `max(cif_id)` (`build_cc_obs_base:207-209`), which ignores NULLs.
Spec/expected: CLAUDE.local "customer signals at CIF level"; one rule per concept across CC and RL;
deterministic outputs (D4 crosstabs need reruns to agree).
Options: (a) keep (accept non-determinism). (b) RL takes the same `max(cif_id)` per grain as CC
(one shared step in `_obs_base`). (c) Fail loud when a grain row has more than one non-NULL
`cif_id`.
Recommendation: (b), folded into the shared bundle; it is a no-op where the spine is clean.
Impact: rows of `rl_spine` with more than one `cif_id` per `(account_id, observation_date)`
(one aggregate in the shared bundle's check: `groupBy(GRAIN).agg(countDistinct(cif_id))`, plus
the NULL-and-non-NULL count). The golden harness avoids this input today (inventory §7).

### S6-Q03 [A4 CC · `cc_a4_deterioration/nodes.py:44-59`, `cc_full_history/nodes.py:52-54`] Restructure flag counts an out-of-range first bucket
Now: `restructure_blind_spot_flag` = 1 when the earliest non-NULL `dlq_bucket` of the account is
≥ 4. The test does not apply the engine's validity range (`0 ≤ bucket ≤ 9`,
`spark.py:160`), so a first row at 10+ (a parsing artefact the engine itself rejects as invalid)
marks the account a blind spot: never EPD, straight roller always seasoned, Q0 → unknown when it
starts delinquent (harness account 12). Separately, `build_cc_full_history` keeps the max bucket
per `(account_id, billing_date)`, so an invalid 10+ row beats a valid row on the same date and the
engine then drops that date as invalid (one fewer observed month, possibly a gap).
Spec/expected: the flag means "opened mid-delinquency" (METHODOLOGY §2, conformance D2); an
invalid value is not evidence of that. (O19 covers the separate data-start censoring question.)
Options: (a) keep. (b) Apply the same validity range in both places: the flag reads the earliest
*valid* row, the per-date max ignores out-of-range values.
Recommendation: (b), in the A4 bundle.
Impact: accounts whose earliest `dlq_bucket` is > 9, and dates with a > 9 row next to a valid row
(`n_invalid_rows > 0` in `crx_cc_dpd_sequences` gives the upper bound). Likely tiny.

### S6-Q04 [A4 RL · `rl_a4_deterioration/chains.py:65,72`, `rl_a4_deterioration/nodes.py:65-70`] NULL dates or candidate counts on a link row break the chain rules
Now: `known = greatest(restr_flagged_date, orig_close_date)` is NULL when both are NULL, and
`candidate_count` may be NULL. `resolve_chains` then takes Python `max(...)` over the walked edges:
with a NULL next to a value it raises `TypeError` (the node fails with no named cause); with a
single NULL edge it returns `None`, so `chain_known_date` is NULL and `before_chain` is false for
every row, i.e. every observation, including those before the restructure, reads the linked
history (the "own history before the known date" rule is lost).
Spec/expected: conformance D6 ("from the later of its restructure flag and the original's
closure"); D2 (missing data fails loud, naming the table).
Options: (a) keep (PROD has run, so today's link has no such rows). (b) Guard: a matched link row
with NULL `known` or `candidate_count` raises a `ValueError` naming `int_loan_restructure_link`.
(c) Treat a NULL `known` as "never known" (the row stays on its own history).
Recommendation: (b), cheap, in the A4 bundle.
Impact: 0 rows in PROD today (B11/B13 ran); protects a refresh of the link table.

### S6-H01 (M) [A3 · `cc_a3_payment_credibility/_signals_common.py:93-97`, RL twin `rl_a3_payment_credibility/nodes.py:437-456`] Window start by `add_months` on month-end dates

`<= observation_date`. On month-end observation dates Spark does not snap (S6-Q07): for

`greatest(anchor, observation_date − N months)`.
Spec/expected: D-A3-6 "as A1 and A2 do (`_common.window_months`)": calendar months, the
observation month included.
Recommendation: the redesigned A3 takes the window start from `_common` (first day of the
observation month minus N − 1 months), then `greatest` with the anchor; say so in D-A3-2.
Impact: CC rows whose previous-month billing date is on a day after the observation month's last
day (billing days 29–31) at 30-day / February observation months.

### S6-H03 (M) [A4 → A3 anchor · `_dpd_journey/core.py:108-141`] What the A4 anchor means on cropped or blind histories
Now: `months_before_spell` is the index of the current spell's start **within the kept history**
(after the CC floor 2024-01, a truncation or the source start). For a cropped history that starts
delinquent (`left_censored`), it is 0: the "spell start" is the first kept month, not the real one.
D-A3-2 uses it as the anchor for Dimension C (the 12 months before it), the Dimension B start and
the DCORE windows. For these rows the 12 months before the anchor lie before the floor, so
Dimension C reads `no_record`, and the DCORE / commitment window starts at the floor instead of
the real episode start. A4 also has no row at all for S6-Q01 rows and (today) for CC obs-base
dates (S6-Q05).
Recommendation: the A3 redesign states the anchor for `history_cropped & starts_delinquent` rows
(e.g. anchor unknown → Dimension C `no_record` flagged as "censored", and windows from the
observation-date lookback only), and D-A3-10's measurement counts these rows separately. Needs
S6-Q05 settled first (A4 on the obs base).
Impact: A4 `unknown` rows (large at 180+: "99% of the gt2y vintage" per `params.py`), plus every
CC row whose spell started before 2024-01.
